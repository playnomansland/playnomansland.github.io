# Game server (Cloudflare Workers + Durable Objects)

Started 2026-11-02. The website stays on GitHub Pages; the server only handles online play. vs AI, solo, devtest and Counter Lab never need it.

## How it is built

- `server/` is a Cloudflare Worker (`server/src/index.js`). Each match or tournament code gets its own Durable Object (`Room`): a small program with its own WebSocket connections and its own SQLite database. Free plan to start; Workers Paid ($5/month) when traffic needs it.
- The server bundles the same `src/engine.js` and `src/game.js` the page uses, so a battle on the server gives exactly the result the phones play back (checked by the test).
- One battle takes about 0.3 s of CPU (0.8 s at most in bot-vs-bot rounds). A Durable Object may use 30 s per message, so there is plenty of room.
- Deploy: `.github/workflows/server-deploy.yml` runs the tests on every push to main that touches the server or the game rules, then deploys if the secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are set.
- Local: `cd server && npm i && npm run dev` (port 8787). Test: `npm test` (starts its own server on 8799).

## Steps

1. Setup (live since 2026-11-02 at https://nml-server.nomansland.workers.dev): `/health`, `/selftest` (one bot round on the server), `/room/<CODE>` WebSocket rooms that relay messages, with the limits below.
2. Tournaments on the server (live since 2026-11-02): `TourRoom` (`server/src/tour.js`) keeps each tournament in its own storage and runs `Tour.apply` for the organizer. Organizer and players each get a secret key; ids are public, keys never are. Bot-vs-bot matches are played by the server. Tournaments are deleted when ended or after 14 days untouched. Matches themselves are still phone-to-phone (step 3). Old tournament history is not carried over.
3. Server as referee (live since 2026-11-02): `Room` (`server/src/room.js`) keeps each live match; the rules are `src/referee.js` (shared with the page and node tests). Phones send actions (`{ t: 'act', seq, fn, a }`: a Game function from `Referee.ACTIONS` and its arguments), never their gold or army. The Room runs them through the same Game functions (which check gold, tiles and unlocks), on that player's side only, only while deploying and before Ready, and acks each with a fingerprint of that side. It runs the deploy clock (alarms), the fight and the round flow, and sends each phone only its view (`Referee.view`). A friend's match: the phone that makes it is side 0 (`hello { create }`), the friend side 1, each with a secret key for reconnects. A tournament match (`/room/<CODE>?t=<T>`): `TourRoom.matchFor` checks the player's tournament key and says the side; the Room reports the result with `TourRoom.serverResult` (Durable Object RPC), and phones' own reports are ignored. Matches are deleted after a day untouched. PeerJS stays as a fallback (Factions, Counter Lab units, a tournament's `net: 'peer'` setting, and when the server can't be reached) until a tournament has run on the server.
4. Match history on the server (built 2026-11-02): the server saves every round of every server match itself; the phones no longer post server matches to the Google Sheet (the Sheet is exported and kept as an archive). Details below.
5. Accounts (live since 2026-11-02: guests and Sign in with Google; details below). 6. Ranked (below).

## Match history (step 4)

- Where: one `HistoryRoom` Durable Object (`server/src/history.js`, named `all`) with its own SQLite table `rounds`. Chosen over D1 for now: it needs no new database, dashboard step or token rights (the deploy token's Workers rights cover it), and it is the same kind of storage as the Rooms. Accounts (step 5) can still go to D1; if history ever needs SQL joins with accounts, it moves there with a one-off copy.
- When: the Room saves a round right after the fight message has gone out to the phones (`Room.record`, called from `broadcastFight`; a forfeit gets a row too). It is a Durable Object RPC call the match never waits for, and any error is logged (`history not saved`) and swallowed: a failing or slow store can't stop or slow a match. `server/test/history.test.js` checks this with a store that always fails (`HISTORY_FAIL_ROOMS`, a test-only setting that production never sets).
- What, per round: room code, tournament code and match id (tournament matches), the match id `<ROOM>-<seed>` (a room's rematch is a new match), round, map, look, both leaders, each army (unit, level, tile), skills bought, tower types, winner, timeout, seconds, damage, health after, match over and match winner, time, and for a forfeit which side gave up. Usernames only for tournament matches. The pre-fight snapshot and the fight summary are kept gzipped (about 1-3 KB a round; dropped if over 64 KB) so replays can be added later.
- Reading: `GET /history?limit=&before=` (newest first, `limit` 1-100, default 40; `before` is the `next` id from the page before) and `GET /history/<match>` (one match, oldest round first; a bare room code gives that room's newest match). Same origin check as the rooms, and at most 60 reads a minute per IP. The page's Match history sheet reads it (Online matches tab); the Phone-to-phone tab and the fallback when the server can't be reached read the Sheet.
- Phone-to-phone (PeerJS) matches still post to the Sheet from the host's phone for now: the server never sees them, and they are the fallback until the server has carried a tournament. They stop when PeerJS goes.
- Retention: rounds are kept for 1 year (`KEEP_DAYS`), then deleted by a daily alarm. No personal data beyond tournament usernames; no IP addresses are stored (the read limit keeps them in memory only for a minute).

## Security: built in from the start

The goal is that nothing has to be redesigned if thousands of strangers show up. Only capacity and moderation tools get added then.

- The server decides. Since step 3 no result, gold amount or army comes from a phone; a modified client can only send actions the rules allow (`node tools/tests/referee.js` and `server/test/match.test.js` try the cheats: unknown functions, extra arguments, wrong types, locked units, bad tiles, no gold, the other side's squads, actions after Ready or the clock).
- Each player and the organizer have their own secret key: nobody can act or report as someone else, and only the organizer's key runs organizer actions, which the server checks against the rules (`Tour.apply`) and a list of allowed settings.
- Limits per connection: messages over 256 KB, more than 40 messages per 10 s (150 in a match room, where every tap is an action), non-JSON or binary messages close the connection. At most 12 connections per room. Codes are 4-8 letters/digits.
- Origin check: only the game's own pages (GitHub Pages, local test servers) can open a connection from a browser. Scripts can fake this, so it is a first filter, not the lock; the referee and the limits are the lock.
- Secrets live in GitHub Actions secrets and Cloudflare, never in the repo. The Cloudflare token is limited to Workers.
- Cloudflare's network absorbs floods (DDoS protection is included on every plan).
- Pinned tool versions and a committed `server/package-lock.json`, so builds are reproducible.

Added when the player count calls for it (no redesign needed):

- Per-IP rate limits on new rooms and sign-ups (Cloudflare rate limiting rules, Turnstile bot check on sign-up).
- Username filter and a report button; admin actions (ban, rename, settle a disputed result) only through the server with an audit log.
- Error alerts, usage and spending alerts, a status page.
- Daily database export (Durable Object SQLite also has 30-day point-in-time recovery; the History object is one database, so one export covers all match history).

## Accounts (step 5)

The idea:

- Play as a guest first: the phone gets a random player id from the server and a username. No sign-up needed to try the game.
- One tap to keep it: "Sign in with Google" (and "Sign in with Apple", which the App Store requires when an iPhone app offers Google sign-in). Later maybe Discord.
- The player's id is our own; Google/Apple are just keys linked to it. Signing in on a new phone finds the same player. A guest who signs in keeps their id and username.
- The server checks Google's and Apple's signed tokens itself, then gives the phone its own session (expires, can be revoked). No passwords stored by us.
- Account deletion removes the login and personal data; past match results stay with an anonymous name.

Built 2026-11-02 (`server/src/accounts.js`, routes in `server/src/index.js`):

- Storage: the D1 database `nml-accounts`, bound as `ACCOUNTS`. The block in `server/wrangler.toml` stays commented out until the database exists; until then every `/account/*` route answers 503 `accounts off` and nothing else changes. The Worker makes its own tables (`CREATE TABLE IF NOT EXISTS`, once per isolate), so no migration step is needed in the deploy.
- Routes, all `POST` with a JSON body (8 KB at most), the same origin check as the rooms, and a preflight answer for the Authorization header:
  - `/account/guest { tag? }` -> `{ player, session }`. A new player `p` + 16 hex digits, username `Guest NNNN` unless one is given.
  - `/account/google { credential }` -> `{ player, session, linked }`. Verifies Google's ID token: RS256 signature against Google's published keys (cached by their max-age, refetched once for an unknown key id), audience = `GOOGLE_CLIENT_ID`, issuer, expiry (1 minute leeway), not issued in the future. `linked` is `existing` (that Google account's player, on any phone), `guest` (the signed-in guest gets the login and keeps id and username) or `new`. The session that made the call ends either way.
  - `/account/me` -> `{ player, session? }`, `/account/tag { tag }`, `/account/signout { all? }`, `/account/delete`. These need `Authorization: Bearer <session>`.
- Developer mode: a player is a developer when they sign in with a Google account whose verified email is in the secret `DEV_EMAILS` (comma separated). It is a Cloudflare secret, put there by the deploy workflow from the GitHub secret of the same name, so no email is in the repo. Checked at every Google sign-in (removing an email takes it away at that account's next sign-in); the email is compared and dropped, never stored; guests are never developers. `player.dev` comes back from every account route; the page's `devMode()` reads it. Rule for the future: every feature that is locked or gated per player lets developers through (on the server by its own `dev` column, never by the phone's word).
- Usernames: 2-16 letters (any language), digits, space, `_ . -`. Not unique.
- Sessions: 32 random bytes; the phone keeps the token (`phonebellum.account.v1`), the server only its SHA-256. 30 days from the last rotation; `/account/me` rotates a session older than a day and leaves the old token working for 5 minutes. At most 10 per player (the oldest go). Tokens only in the Authorization header, never in URLs or logs.
- Limits per IP (the IP kept only as a hash, for the length of the window): 20 guest requests an hour, 30 Google sign-ins per 10 minutes, 120 other calls a minute. A tournament on one wifi stays well inside these.
- What is stored: `players` (id, username, created, last seen, deleted, dev), `logins` (provider, Google's subject id, player), `sessions` (token hash, player, created, expires), `hits` (rate-limit counters). No email, name or picture from Google. Deleting an account removes its logins and sessions and blanks the username; the id stays as a tombstone so past results can point at an anonymous player. Account rows have no expiry; sessions end after 30 days.
- The page: Account on the start screen (`openAccountSheet` in `src/site-template.html`). Nothing is created until the player taps Play as a guest or signs in. Google's script (`accounts.google.com/gsi/client`) is loaded only when the sheet opens and `GOOGLE_CLIENT_ID` is set in the page.
- Not yet (next; no longer waiting for a tournament): tournament players and match history rows linked to player ids, so a player's history follows the account. A guest who signs in to a Google account that already has a player becomes that player; the old guest is left as it is (it has no history to move yet).
- Tests: `server/test/accounts.test.js` (in `npm test`; signs its own Google-style tokens against a local key server, checks every route, rotation, limits and refusals) and `node tools/tests/account-ui.js` (the sheet in the browser with a fake Google button; needs `python3 -m http.server 8766`). Both run against a local D1 database (`server/test/accounts-env.js`).
- Setup (done 2026-11-02): D1 database `nml-accounts` bound in `wrangler.toml`; the deploy token has Account / D1 / Edit; GitHub secret `DEV_EMAILS` (Vilhelm's Google email); Google OAuth client (Google Auth Platform, Web application, origins snetendare.github.io, playnomansland.github.io and the two local test servers) with its id in `[vars]` and the page's `GOOGLE_CLIENT_ID`. A new site address must be added to the client's origins and to `ALLOWED_ORIGINS`.

## Ranked play and the leaderboard (2026-11-02)

- A ranked match is a friend's match on the Room with hello { create, ranked: true, session }. Both phones send their account session in hello (never in the URL); the Room checks it with accounts.js sessionPlayer. No account: denied { why: 'account' }; a guest (no Google login, not a developer; since 2026-11-04): 'login', and the page opens its "Log in to play ranked" sheet, then tries again; the same player on both sides: 'self'; switched off: 'ranked off' (developers may still create one). Normal friend's matches still take guests.
- Settings are fixed by the server (room.js RANKED): map testgrid ("Standard"), packOptions 5, mirror, offChars ['blixten']; only the creator's look is kept.
- meta.ranked keeps the series ({ ids, tags, wins, ties, games, done, result, forfeit, counted }); tally() counts each finished game once (by seed). Best of 3: 2 wins, or 3 games (equal wins = a tie). A forfeit loses the series. When decided, recordSeries adds w/t/l to D1 table ranked. Rematch = next game; after a decided series, a new series. welcome, lobby, sync, fight and forfeit carry ranked.
- D1 tables: ranked (player, w, t, l, updated) and config (k, v; 'ranked' = 'on' | 'off'). POST /account/ranked { on } (developer only, the server's dev column) switches it; /account/me returns rankedOn. GET /leaderboard (origin-checked) -> { on, rows: [{ id, tag, w, t, l, score }] }, best score first (since 2026-11-03: 75 x wins / the most wins on the board + 25 x win share, a tie counting as half a win; BOARD_SQL in accounts.js), deleted accounts left out. Leaving a match while the opponent is disconnected (Room 'forfeit' while R.away of the other side) counts as their forfeit, not the leaver's.
- Tests: server/test/ranked.test.js (in npm test), tools/tests/ranked-login-ui.js (browser, port 8777: the login sheet for the host and for a friend opening the link).

## Titles (2026-11-02)

- accounts.js titlesOf(player): 'dev' (players.dev) and 'day1' (players.created before DAY1_END = 2026-11-09 00:00 Stockholm). players.title (added by ensureSchema with ALTER TABLE) is the pick: an id, 'none', or NULL (= the first earned). Player objects carry titles and title; POST /account/title { title } ('' = none; only an earned title). The leaderboard rows and the ranked series (titles) carry the shown title. Page: TITLES, nameplate(), popup for titles not yet announced on this phone (pb-titles-seen).
- Legend title (2026-11-03): gold, for the top LEGEND.top (5) of the leaderboard when a Stockholm month ends, kept for good. The Worker's hourly cron ([triggers] crons = "7 * * * *", index.js scheduled) calls accounts.js awardLegends: once the clock is past a month (LEGEND.first = '2026-11') not yet in config 'legend_month', the top 5 by the leaderboard's order (BOARD_SQL) get an 'awards' row (player, title, period, place) and players.legend is recounted. Idempotent. The board is not reset. GET /leaderboard also returns legend { top, ends }. LEGEND_NOW (ms) is a test-only stand-in for the clock. Tests: tools/tests/legend.js (headless, node:sqlite as D1), server/test/ranked.test.js (the cron through wrangler --test-scheduled).

## Puzzles: the Initiate title (2026-11-03)

- The light blue title 'initiate' (titlesOf: players.initiate set) for solving every Easy tutorial puzzle (src/puzzles.json). Since 2026-11-05 each puzzle has a `level` (Easy, Medium); the Easy ones come first in the file (accounts.js refuses to load otherwise) and only they count: PUZZLE.initiate = their number (3), PUZZLE.count = all puzzles (the valid k range). The Medium puzzles are replayed and saved the same way but are extra practice, so the title kept its meaning and players who earned it with three puzzles keep it. Table puzzles (player, k, created), one row per solved puzzle; player objects carry puzzles [k, ...].
- POST /account/puzzle { k, army: [[unit name, col, row], ...] } (auth) -> { player, won, solved }. The server doesn't take the phone's word: accounts.js puzzleWon sets the fight up exactly as the page's startPuzzle does (the built-in units via server/src/puzzle-data.cjs, the Old standard board, the enemy's squads as if from an earlier round, the puzzle's gold and shop), places the sent army with Game.place (so a tile outside the zone, a unit the puzzle doesn't sell or more squads than the gold buys fail) and plays it with Referee.fight: side 0 must win without a timeout. An already solved puzzle answers won: true without replaying. Solving the last Easy one sets players.initiate (counting rows with k < PUZZLE.initiate); ~0.1 s a replay.
- POST /account/music { music: { prefs, playlists } } (auth) -> { music } (2026-11-07). The music player's settings and the player's own playlists, kept as JSON in players.music and sent back as player.music in every answer that carries the player (null = never saved). accounts.js cleanMusic keeps prefs to known fields (volume and sound effect volume 0-100, Music / Sound effects / Shuffle / Repeat / chat / emotes on or off, src 'menu' | 'all' | 'u:<id>', song) and up to MUSIC.lists (20) playlists of up to MUSIC.songs (80) song ids, each with an id ([a-z0-9]{1,12}) and a name (1-24 characters, control characters and < > dropped). Song ids are only checked for shape. Its body may be up to ACCOUNT.MUSIC_BYTES (24 KB). Deleting an account clears it.
- The page keeps a win's army in localStorage (phonebellum.puzzle-wins.v1) until the server has counted it (acct.puzzles), and sends waiting ones after every account answer (acctTake -> puzzleSync), so puzzles solved signed out count once the player has an account.
- Tests: server/test/invites.test.js (puzzle section), tools/tests/initiate-ui.js (browser, port 8787).

## Invite a friend (2026-11-03)

- Reward: the limited Aquamarine Ether Golem skin (INVITE.skin), to the inviter, once (however many friends come).
- Only a confirmed account invites: POST /account/invite (auth) answers 403 'google needed' for an account without a Google login, else { code, friends: [{ tag, google, played, done }], rewarded, skin, minFights }. The code (table invites: code, player, created) is 6 letters without look-alikes, made once per player. The link is the page with ?invite=CODE.
- The friend's account: guest, google and me take { invite }. claimInvite ties the account to the inviter (table referrals: friend, inviter, created, played, done) only if it is new: made within INVITE.claimMs (24 h), no online match finished yet, not the inviter, inviter not deleted and Google-linked. One inviter per friend (the first). The page keeps the code from the link (pb-invite, 14 days) and acctCall sends it with the next guest / google / me call, then drops it.
- Done when the friend has (1) a Google login too and (2) finished an online match. settleReferral runs after a Google sign-in and after every counted match, so either order works; it marks the referral done and gives the skin (src 'invite', worn).
- Online match (countOnline, called from room.js ended()): a friend's or ranked match on the server, over, with at least INVITE.minFights (3) fights. Each side with an account counts unless it left (forfeit; the Room keeps meta.left = { seed, side }) or both sides are the same player. Counted once per match (meta.onlineCounted = the match seed); players.online += 1 and referrals.played is set. The Room keeps the players' ids in meta.pids (never sent to phones). Tournament matches (no session in hello) and 2v2 don't count.
- Why it's hard to farm: both accounts must be Google accounts, the friend's account must be brand new and finish a real 3+ fight match without leaving, and the reward comes once.
- Page: rewards card on the main menu (pictures of both rewards) -> Rewards sheet (openRewardsSheet: link, Copy / Share, friends' progress; sign-in prompt for guests). The welcome screen says when a friend's link was opened.

## Bug reports (2026-11-04)

- `POST /account/bug { text, version, match, info }` (session optional) -> `{ ok, url }`. The Worker calls the Discord webhook `BUG_WEBHOOK` (a Cloudflare secret; the deploy workflow copies the GitHub secret `DISCORD_BUG_WEBHOOK`) with `?wait=true`, so a forum channel makes a new post: `thread_name` = the first line of the text (90 characters at most), `content` = the text plus Version, Match, the known `info` keys (mode, round, phase, map, board, device, screen, page) and the player (username and id, or "not logged in"). `allowed_mentions: { parse: [] }`, so a report can't ping anyone. `url` = `https://discord.com/channels/<DISCORD_GUILD_ID>/<new post>`.
- Optional var `BUG_TAG`: a forum tag id put on every post (needed if the forum requires tags).
- Limits: per IP 5 reports per 10 minutes (bucket `bug`), text 3-1500 characters, other fields 160. Errors: 503 `bugs off` (no webhook set), 400 `too short`, 429, 502 `discord` (with `code` = Discord's status).
- `/account/me`'s `discord` object carries `bugs` (true when the webhook is set).
- The page falls back by itself (copies the report, opens the Discord invite) when the call fails for any reason.
- To switch on: in Discord, #bug-reports > Edit channel > Integrations > Webhooks > New webhook > Copy webhook URL; on GitHub, add it as the repository secret `DISCORD_BUG_WEBHOOK`; then run the "Server deploy" workflow by hand (a deploy only runs on pushes that touch the server, and secrets are uploaded at deploy time).

## GG, My matches and replays (2026-11-04)

- **GG:** room message `gg` from a player once the match is over, once per side and match (`meta.gg = { seed, sent }`, also in every sync as `gg`). Relayed to everyone in the room as `{ t: 'gg', from, gg }`. When both sides have accounts, they aren't the same player, the match had `GG.minFights` (3) fights and nobody left it, it is saved in D1 table `ggs (giver, receiver, match, created)` (`accounts.js recordGG`). `ggCount` counts at most `GG.perGiver` (3) GGs from one giver; at `GG.need` (10) `players.goodsport` is set and the **Good sport** title (pale sky blue) is earned for good. Player objects carry `gg` (the counted number). Order of titles: DEV, Legend, BABABABA, Initiate, Good sport, Day 1.
- **Usernames in history:** rows now carry `names` for any side whose phone had an account (before: tournament and ranked only) and `ranked`.
- **Who played:** history rows keep `p0`, `p1` (account ids of side 0 and 1; tournament matches none). Never sent out.
- **My matches:** `POST /account/history { before? }` (session) → `HistoryRoom.mine(player, before, 15)` → `{ matches: [{ matchId, side, rounds }], next }`, newest first, paged by the newest row id of each match.
- **Replays:** each round's replay is now saved with the units it was played with (`Ref.withUnits(pre)`), so it plays back the same after balance changes (an engine change can still change it). `GET /history/<match id>?replay=<round>` → `{ pre, summary }` (404 if not kept; same origin check and per-IP limit as `/history`).
- Tests: `server/test/gg.test.js` (in npm test, port 8779), `tools/tests/gg.js` (headless counting and title rules), `tools/tests/gg-history-ui.js` (two phones, port 8778).

## Online lobby, chat and emotes (2026-11-04)

Design: `docs/LOBBY.md`. Built on branch `lobby`, merged to main 2026-11-04.

- `LobbyRoom` (`server/src/lobby.js`): one Durable Object named `all` (binding `LOBBY`, migration `v5`). Route `/lobby`: a WebSocket, or a plain `GET` for the list once (developer-only cards left out). Same origin check as the rooms. Listings are kept in memory and in the object's own storage; a listing not heard from for 3 minutes (`LOBBY.staleMs`) is dropped by the lobby's alarm.
- Listing: `{ code, kind: 'match'|'duo', mode: 'standard'|'ranked'|'2v2', host: { tag, title }, map, look, players, seats, phase: 'waiting'|'playing', round, watchers, spectate, dev, at }`. `dev` is set by the lobby for 2v2 while config `lobby_duo` is `'dev'`; such cards only go to lobby sockets whose session is a developer (`sessionPlayer`, the server's own `dev` column).
- Lobby messages: in `hello { session? }`, `quick { not? }`, `ping`; out `rooms { list, dev }` (on hello), then `room { listing }` / `gone { code }` (changes, batched once a second), `quick { code }` (the oldest open public Standard room; never ranked, never 2v2, never the asking account's own room) or `quick { create: true }`, `pong`.
- Rooms report by DO RPC: `LobbyRoom.upsert(listing, owner)`, `drop(code)` and `claim(ip)` (may this IP make one more public room). `Room` / `DuoRoom` (`listing()`, `report()`) send their card on: created, join / leave, start, each new round, settings, spectate toggle, watcher count (at most every 5 s), and every 60 s while public (the room's alarm, which then never touches the match: `Ref.due` still in the future means a heartbeat only). They drop it when the match is over, the host leaves the waiting room, or a waiting room has had nobody come or go for 10 minutes. A report is never awaited by the match and errors are only logged.
- Room messages added: `hello { create, public, spectate?, map?, skin? }` (a public room), `spectate { on }` (host, any time; off closes watchers with `denied { why: 'no watchers' }` and turns new ones away), `public { on }` (host, before the start), `chat { text }`, `emote { id }`, `report`. Out: `roomset { pub, spectate, chat }` (chat: this phone may type), `chat { from, tag, text, at, w? , team? }`, `chatLog { lines }` (on hello: the lines that phone may see), `chatMerge { lines }`, `emote { from, id }`, `reported { ok, why? }`, `denied { why: 'slow down' | 'sign in' }` (the phone stays in the room). A public waiting room gives side 1 to a new player when the one who had it is gone — but never to the account that already has side 0: that gets `denied { why: 'here' }` (nobody is in the same room twice; its own phone still comes back by its key, and a ranked room keeps `'self'`). Ranked rooms still need an account logged in with Google to create and to join.
- Rooms close themselves (2026-11-04): `EMPTY_MS` (a minute, `ROOM_EMPTY_MS` for tests) after the last socket leaves, a room with no match running drops its card, `deleteAll()`s its storage and forgets its keys, so the code answers `nomatch`; the room's alarm is pulled in to that moment when the last socket goes (`Room.gone` / `canClose` / `close`, the same in `DuoRoom`). A match that has started plays on without the players and ends by itself; the room closes once it is over, and a tournament match only after its result has reached the tournament. The old one-day `KEEP_MS` sweep stays as a backstop.
- Chat (`server/src/chat.js`, `limits.js` CHAT): text only from a session with a Google login (`sessionPlayer` now returns `google`); guests send emotes (`bababa`, `golem`, `shock`). Lines are trimmed, control characters removed, at most 120 characters, a short word filter (`***`; whole words only for the short ones, so Swedish "slut" passes). Per sender 3 lines / 5 s and 20 / minute, one emote / 3 s. The room keeps the last 50 lines in its own storage (deleted with the room), never in match history. Watchers' lines go to watchers only while the match runs (`hid`, with the match seed); when it ends (result or forfeit) the players get them in `chatMerge` (before the `forfeit` message) and from then on every line goes to everyone; a rematch splits them again. 2v2: `chat { team: true }` goes to the teammate only; the lobby's emotes go to all four, the old quick lines (`Duo.EMOTES`) stay team-only.
- Report: `report` from a player posts the room's own last 20 visible lines, both gamertags and the match id to the Discord webhook `REPORT_WEBHOOK` (a Cloudflare secret; the deploy copies the GitHub secret `DISCORD_REPORT_WEBHOOK`; optional var `REPORT_TAG` for a forum that needs tags). Limits: 5 per 10 minutes per IP (bucket `report`) and 3 per phone per room. Off (`reported { ok: false, why: 'reports off' }`) until the secret is set.
- Limits (`limits.js` LOBBY): 3 lobby sockets per IP, 30 lobby messages / 10 s per socket, 10 public rooms per 10 minutes per IP (in memory in the lobby; private rooms aren't limited), one listed room per player (by account, guests by hashed IP: a new public room takes the old card's place), at most 200 listings (the oldest waiting room makes way; it stays joinable by code). No IP is stored: rooms keep a short hash in the socket's attachment.
- `lobby_duo` (D1 `config`): `'dev'` (default) or `'all'`. `POST /account/lobbyduo { v }` (developer only) flips it, no deploy needed; the lobby re-reads it once a minute. When `'all'`, 2v2 cards go to everyone and anyone may make a 2v2 room.
- Test-only settings (never set in production): `LOBBY_TEST` (`GET /lobby?fake=CODE` lists a card that sends no heartbeat), `LOBBY_HEARTBEAT_MS`, `LOBBY_STALE_MS`, `LOBBY_IDLE_MS`, `ROOM_EMPTY_MS`.
- Tests: `server/test/lobby.test.js` (listings appear and vanish, join, watch, spectate toggle, quick play, ranked needs an account, 2v2 only for developers and `lobby_duo`, 2v2 Team / All chat, heartbeat and expiry, one room once and empty rooms closing, limits; port 8780) and the chat part of `server/test/match.test.js` (signed-in only, filter, limits, emotes, watchers apart during the match, merged at the end, split on rematch, reconnect, report), both in `npm test`; browser: `tools/tests/lobby-ui.js` (8781), `tools/tests/chat-ui.js` (8782).
- Not built yet: the ranked queue (LOBBY.md §5), a block list, lobby-wide chat.

## Friends, game invites and private messages (2026-11-04)

Design: [FRIENDS.md](FRIENDS.md). For signed-in players only (a Google login; a bare guest gets 403 `google needed` and no hub). Friends are stored by player id, so a username change keeps them.

- D1 tables (made by `accounts.js` like the others, `FRIEND_SCHEMA`): `friends (a, b, since)` one row per pair with `a < b`; `friend_requests (sender, target, created)` (30 days, `FRIENDS.requestMs`); `dms (pair, sender, text, created)` with an index on `(pair, created)`, `pair = a:b`, the last 100 per pair kept (trimmed on insert); `dm_read (player, pair, at)` (unread = newer messages from the other); `friend_mutes (player, muted)`. New `players` columns `hub` (the status as JSON while a hub socket is open) and `hub_at` (when the hub last wrote it: older than 5 minutes counts as offline, in case a hub was stopped by a deploy).
- Routes (POST, session in the Authorization header): `/account/friends` -> `{ friends: [{ id, tag, title, online, status: { where, round? }, seen, since, unread, muted }], incoming, outgoing, max }` (online first, then by last seen); `/account/friend/add { tag | id }` -> `{ ok, sent | friends, player }`, or `{ several: [{ id, tag, title }] }` when several signed-in players have that username (the page lets the player pick, then adds by id); `/account/friend/accept|decline|cancel|remove { id }`; `/account/friend/mute { id, on }`; `/account/dm/list { id, before? }` -> `{ lines: [{ k, from, text, at }], more }` (oldest first, pages of 30, `before` = the oldest `k` held); `/account/dm/read { id }`; `/account/dm/report { id }`. A lookup by username returns only `{ id, tag, title }`. `/account/me` carries `friends: { requests, unread }` (null for a guest). `/account/delete` removes the player's friendships, requests, messages, read marks and mutes. Declining, cancelling and removing are silent (the other side's hub gets `removed`, which only refreshes its list). Removing a friend deletes the pair's messages.
- Limits: 100 friends, 20 outgoing requests waiting, 20 new requests a day per player, 30 username lookups per 10 minutes per player (per-player counters in `hits`); private messages 300 characters (control characters stripped, `text.js` word filter), 5 per 10 s per hub (memory) and 60 an hour per player (in `hits`, so trimming a pair can't make room); invites 10 a minute, one open invite per friend; reports 5 per 10 minutes per IP and per player.
- PlayerHub (`server/src/hub.js`, binding `HUB`, migration `hub-1`, after the lobby's `v5`): one Durable Object per player, named by the player id. The page opens `GET /hub?p=<player id>` (WebSocket, origin-checked) and sends `hello { session }`; the hub checks that the session is that player's and a Google account (`denied { why: 'session' | 'google' }` otherwise) and closes sockets that haven't said hello within 10 s. At most 8 sockets (phones and tabs) per player, 40 messages per 10 s per socket; pings are answered without waking the hub.
  - In: `status { where: 'menu'|'room'|'match', code?, round? }` (the page sends it on every change and every 2 minutes), `invite { to, code, mode? }`, `inviteCancel { code }`, `decline { code }`, `dm { to, text }`.
  - Out: `welcome { id, invites }` (open invites to this player), `status { id, online, status, seen }` (a friend's dot; never a room code), `request { from }`, `accepted { by }`, `removed { by }`, `invite { from, code, mode, expires }`, `invited { to, code, expires }`, `inviteFail { to, why: room|not friends|offline|open|slow down }`, `inviteGone { from?, code }`, `declined { by, code }`, `dm { from, to?, text, at, k }` (the sender's own phones get it with `to`), `dmFail { to, why }`.
  - Presence: a player's status is the busiest of their phones (match, then room, then menu). On a change the hub writes it to `players.hub` and calls each friend's hub (RPC `friendStatus`), which forwards it to that friend's sockets. When the last socket closes, `hub` is cleared and `players.seen` set (Last seen).
  - Invites: only to a friend whose hub has a socket open (RPC `presence`), only for a room code one of the inviter's phones is in. The invite is kept in both hubs' storage (`out:<friend>`, `in:<inviter>`) for 5 minutes (alarm). It goes (`inviteGone`) when it expires, when the inviter sends `inviteCancel` or none of their phones is in that room any more, or when the friend declines (`declined` to the inviter). The friend's status showing that room's code marks it used. `room.js` is not changed: Join is the normal `hello {}` to `/room/CODE`, and a room that has filled or started answers `full` / `nomatch` as before (the page says "That match has already started").
  - Messages: friends only; checked, saved to D1 (`saveDm`), sent to the sender's phones, then to the friend's hub (RPC `deliver`) unless the friend muted the sender (then kept, but not delivered live or counted unread).
  - The account routes call the hubs too (RPC `event`): a request, an accept, a removal.
- Reports: `dm/report` posts the thread's last 20 lines, both usernames and ids and the time to Discord, with `allowed_mentions` empty. Its own channel: the Cloudflare secret `REPORT_WEBHOOK` (the deploy workflow copies the GitHub secret `DISCORD_REPORT_WEBHOOK`); until that is set, reports go to the bug-report forum (`BUG_WEBHOOK`) as their own posts. 503 `reports off` when neither is set.
- `server/src/text.js` (private messages): `cleanText(s, max)`, `filterWords(s)` (a short list, `***`), `rateOk(state, key, n, ms)`. Room chat uses its own `cleanChat` in `limits.js` (the lobby work); the two can be merged later.
- Test-only settings (never set in production): `HUB_INVITE_MS`, `HUB_DM_BURST` (`n,ms`), `HUB_DM_HOUR`.
- Tests: `server/test/friends.test.js` (port 8782) and `server/test/hub.test.js` (port 8783), both in `npm test`; `node tools/tests/friends-ui.js` (two browsers, port 8782).


## Players online (2026-11-10)

How many people have the game open right now, for developers only (the owner asked for it). The friends hubs only see Google accounts, so this is separate and counts every open page: guests and visitors with no account too.

- OnlineRoom (`server/src/online.js`, binding `ONLINE`, migration `online-1`): one Durable Object (`'all'`). Every page keeps one socket to `GET /online?d=<device>` (WebSocket, origin-checked; `device` is a random id the page keeps in localStorage as `pb-device`, so several tabs of one browser count once). The sockets hibernate and pings are answered without waking the object, so an open page costs nothing between pings. Each socket is tagged with its device and a hash of its IP (never the IP); at most 30 sockets per IP and 20,000 in all (`ONLINE`).
- Counting: a device counts while one of its sockets pinged (or connected) within the last 90 s (`ONLINE.staleMs`; pages ping every 30 s), so a phone that went to sleep without closing drops out by itself.
- Route (POST, session in the Authorization header): `/account/online` -> `{ online, at }`, developers only (the server's own `dev` column; 403 `not a developer` otherwise).
- The page (`onl*` in `src/site-template.html`): the socket opens on every page, retrying from 4 s up to every 5 minutes; a developer's page asks for the count every 20 s while in view and shows it in `[data-online]`: a pill under the name on the phone menu (`.online-np`), the first item of the Diorama's top bar (with the DEV tag). `window.__online()` with `?test`.
- **Who is online (2026-11-10):** tapping the pill (phone menu, or the Diorama's top bar item) opens **Online now** (`openOnlineSheet` in `src/site-template.html`): the players signed in on an open page, with their username, title, Google or Guest, how many of their devices are open, and how many open devices have no account; Refresh, and it refreshes with the count every 20 s while open. Each page sends `{ t: 'hello', session }` on its socket when it connects and when it signs in or out (`onlHello`, from `acctSave`); the OnlineRoom looks the session up itself (`accounts.js sessionId`) and keeps only the player id on that socket, so a page can't pass for someone else, and the newest hello wins. At most 6 hellos a minute per socket (`ONLINE.hellos`). Each row also says which screen of the game that player is on (2026-11-10): the page sends `{ t: 'where', w, r? }` when it changes (`onlWhere`, checked every 2 s): `menu`, `room` (a waiting room), `ai`, `online`, `peer`, `puzzle`, `watch` or `replay`, with the round in a match; a player on two devices shows the busier one (`ONLINE.rank`), at most 30 a minute per socket (`ONLINE.wheres`). Only the game's own screens: nothing about where anyone is in the world. Pages with no account send it too but are only counted. `POST /account/online { list: true }` -> `{ online, players: [{ id, tag, title, google, dev, devices }], anon, at }` (developers only; usernames and titles read from the database at that moment, `onlinePlayers`).
- Test-only setting (never set in production): `ONLINE_STALE_MS`.
- Tests: `server/test/online.test.js` (port 8784, in `npm test`); `node tools/tests/online-ui.js` (the page against a local server, ports 8766 and 8788).

## Games played per day (2026-11-10)

How many games were played each day, and nothing else about them (the owner asked for it: the match history only has online matches, games vs the computer were never sent anywhere).

- GamesRoom (`server/src/games.js`, binding `GAMES`, migration `games-1`): one Durable Object (`'all'`) with a `counts (day, kind, n)` table. Days are UTC dates. A game counts once, when its first round is fought.
- Kinds: `online` (server-refereed matches, tournaments included; counted by the Room itself in `record`, round 1, so a page can't send it), `ai` (vs the computer, tournament bot matches too), `peer` (phone to phone, sent by the host only) and `puzzle` (the tutorial and tutorial puzzles).
- `POST /games` `{ kind, d, s }` (the game's origin only; text/plain, so no preflight): `d` the page's device id (`pb-device`, the one `/online` uses), `s` the match seed. A `(kind, device, seed)` is remembered for 2 days (`seen` table, daily alarm) and counts once, so reloads don't count twice. At most 300 games per IP (hashed) per UTC day (`GAMES.perIpDay`).
- `GET /games?days=N` (default 7, at most 366) or `GET /games?day=YYYY-MM-DD`, no account or origin needed: `{ days: [{ day, total, ai, peer, online, puzzle }] }`, newest first.
- The page (`countGame` in `src/site-template.html`, called from `runFight`): not from a local page (localhost) talking to the live server, so tests and local play don't count; with `?server=` it does.
- Check: `server/test/games.test.js` (in `npm test`).
